# Style guide

Every chapter follows this guide. `make lint` enforces the parts a machine can check. The rest
is on the author and the reviewer.

## Who reads this

Engineers who know classic system design (load balancers, queues, caches, databases, sharding)
and now have to design systems where the component doing the work is a model. They are busy and
they are sceptical. Write for the one who will check your arithmetic.

## Voice

- Lead with the point. The first sentence of a section says what the section concludes.
- Concrete beats general. "A 70B model in FP8 needs 70 GB for weights" beats "large models need
  a lot of memory".
- Opinions, with the reason and the condition that would change them. Every chapter recommends
  something.
- Second person is fine. Short paragraphs: four sentences is a lot.
- British spelling: optimise, organisation, behaviour, colour, analyse. Code, API names and
  product names keep their own spelling (`tokenizer`, `max_tokens`).
- No em dashes and no en dashes. Rewrite the sentence with a colon, a full stop, commas or
  parentheses. Write ranges as "200 to 400 ms".
- No filler. The linter rejects the usual offenders (see `tools/lint_prose.py`). If a sentence
  survives with a word deleted, delete the word.
- No "Conclusion" or "Summary" sections. The trade-offs table at the end of each system chapter
  does that job.
- Lists are for things that are actually parallel. An argument is prose.

## Numbers

- Every number is one of three things, and the text says which:
  1. **Arithmetic** shown on the page, with its inputs.
  2. **A price** from `data/prices.toml`, dated, with a source. Prices never appear as literals
     in chapter text: use `{{< var ... >}}` or a generated table, so `make costs` can refresh
     them.
  3. **A rule of thumb**, worded as one ("expect", "typically") with the reason it holds.
- Worked scenarios are illustrative, and the text says so the first time ("in this worked
  example"). Never present an invented measurement as a benchmark result.
- Round honestly. Two significant figures is usually enough. Show the unrounded inputs.
- Money is USD. Token counts are written 2,400 or 2.4K; per-million prices are "$/M tokens".

## System chapter structure

The headings are fixed so readers can jump between chapters. `tools/check_structure.py`
checks them in this order:

1. `## The brief`: the request as a stakeholder would say it, vague parts included.
2. `## Questions to ask`: a table of question, why it changes the design, and the answer this
   chapter assumes.
3. `## The numbers`: back of the envelope, arithmetic shown.
4. `## Version 0`: the simplest thing that could work, with a diagram.
5. One `## Where ... breaks` (or `break`) section per failure, each followed by the next `## Version N`.
   Every break cites evidence: an eval result, a load test, a cost line or a latency budget.
6. `## The final design`: the full diagram and a component table.
7. `## Deployment`
8. `## Cost`: generated tables at three scales.
9. `## Optimisation`: techniques from F5 by code (O1 to O20), each with its saving.
10. `## Operating it`: what to measure, what pages someone, failure modes.
11. `## Variants`: "if the requirement were X instead".
12. `## Trade-offs`: one table, decision, alternative, why.

## Diagrams

D2 sources live in `diagrams/<chapter>/`, rendered SVGs in `images/<chapter>/`. Every diagram
imports `diagrams/_theme.d2` and uses its classes. The theme is generated from the design tokens by
`make tokens`; never set colours by hand.

| Class | Use for |
|---|---|
| `actor` | People and external callers |
| `svc` | Code we run |
| `model` | A model call, hosted or self-hosted |
| `store` | Databases, indexes, object storage |
| `queue` | Queues and streams |
| `ext` | A third-party service we do not run |
| `new` | Added in this version (combine: `class: [svc; new]`) |
| `gone` | Removed in this version, still drawn faded |

Edges: solid is the request path, `async` (dashed) is background work, `offline` (dotted) is
ingestion or batch. A diagram earns its place by showing something the prose cannot. Labels are
two to five words.

## Styling

Every colour, face, radius and shadow comes from `docs/design/tokens.json`, generated by
`tools/tokens.py` (`make tokens`). `theme/book.scss` uses only the `$t-*` variables it produces.
`make design-lint` fails on a colour literal anywhere in `theme/` outside the generated token
files, and on one in a diagram source. To add a colour, add a role in `tools/tokens.py`, run
`make tokens`, and use the new variable or class.
